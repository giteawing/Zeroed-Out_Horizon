# Тестирование и регрессии

## Команды и среда

```bash
npm ci
npm run build
npm test
npm run test:e2e
npx playwright install chromium
```

- CI использует Node.js 22, `npm ci`, сборку, полный Vitest-набор, затем
  Playwright Chromium и desktop E2E.
- `npm test` выполняет файлы `tests/**/*.test.ts`; окружение по умолчанию
  Node. DOM-тесты включают happy-dom директивой в начале файла.
- `npm run test:e2e` через Playwright сам выполняет production build и
  поднимает `vite preview` на `127.0.0.1:4173`. Локально сначала поставь
  Chromium через `npx playwright install chromium`.
- В CI при падении сохраняются `playwright-report/` и `test-results/`;
  изучай trace, screenshot и error context до правки теста.

### E2E там, где `npx playwright install` недоступен

В песочницах без доступа к CDN Playwright браузер не скачивается. E2E
всё равно можно и нужно прогнать — на своём Chromium:

```bash
E2E_CHROMIUM_PATH=/путь/к/chromium \
E2E_CHROMIUM_ARGS="--no-sandbox --disable-gpu" \
npm run test:e2e
```

- `playwright.config.ts` читает обе переменные; в CI они не заданы, там
  работает браузер из `playwright install`.
- Chromium без системной установки даёт npm-пакет `@sparticuz/chromium`
  (ставь во временный каталог, не в проект): `executablePath()` распаковывает
  бинарник, а архивы `bin/al2023.tar.br` и `bin/fonts.tar.br` — библиотеки и
  шрифты. Каталог с библиотеками укажи в `LD_LIBRARY_PATH`, со шрифтами —
  в `FONTCONFIG_PATH`.
- Не добавляй `--single-process` и `--no-zygote`: браузер закрывается между
  тестами, и прогон падает с «Target page, context or browser has been closed».
- Если своего Chromium тоже нет, так и напиши в отчёте: «E2E не запускался»,
  а не «E2E зелёный».

## Как добавлять тест

1. Сначала сформулируй наблюдаемую ошибку и сценарий воспроизведения.
2. Для бага добавь regression-тест, который падает до исправления и проходит
   после него. По возможности тестируй публичное поведение, а не private-поля.
   Тестируй код, которым пользуется игра: функция, которую вызывают только
   тесты, зелёная при любом поведении игры. Такой экспорт или публичный член
   класса роняет `tests/dead-code.test.ts` — подключи его к игре или удали
   вместе с тестами, а проверяемое свойство перенеси на работающий код.
   Геттер, нужный только тестам для наблюдения, вноси в `ALLOWED_MEMBERS`
   того же теста с причиной.
3. Экономический тест проверяет итоговый поток (объём, деньги, расходы, налог,
   потери), а не только вспомогательную функцию.
4. Тест состояния проверяет старый/неполный сейв, нормализацию и
   сериализацию.
5. DOM-тест проверяет реальное содержимое, состояние disabled/locked,
   обработчики и доступность элементов.
6. E2E проверяет путь игрока на собранном приложении: запуск, действия,
   визуальное состояние, сохранение, финал.

## Устойчивость тестов

- Предпочитай детерминированный RNG seed и фиксированные игровые входные данные.
- Не используй реальные задержки там, где можно продвинуть игровой таймер
  напрямую. В Playwright ожидай конкретное состояние через `expect` и
  `expect.poll`. Пауз в E2E нет совсем: `tests/harness.test.ts` отклонит
  `waitForTimeout` и `setTimeout` в сценариях.
- Приёмы вместо паузы — помощники в начале `tests/e2e/smoke.spec.ts`:
  - «ничего не произошло» — проживи кадры (`frames`) и сравни состояние
    целиком: игровой цикл идёт по кадрам, а не по времени теста;
  - «игрок отсутствовал» — сдвинь часы страницы через `page.addInitScript`
    (игра берёт время только из `Date.now()`), а не правь сейв руками:
    уходящая страница при перезагрузке сохраняется сама и затрёт правку;
  - сейв читай после `page.reload()`, а не до: по той же причине он уже
    другой. Величины, которые растут сами (`totalSold`, `playtimeMs`),
    сравнивай с записанным в хранилище, а не с числом, снятым до ухода;
  - «это та же партия или новая» — оставь след, который сам не меняется
    (`fixContractFlow`), и проверь его после действия.
- Не завязывай тест на порядок не связанных карточек, случайные ID DOM или
  внутренние имена методов, если есть стабильный пользовательский селектор.
- Пользовательский текст проверяй по актуальному содержимому
  `src/content/texts.json`. При изменении текста обнови ожидаемое значение,
  но сначала проверь, что смысл и поведение остались правильными.
- Не исправляй красный тест простым удалением assertion, увеличением timeout
  или заменой проверки на `toBeVisible()` для любого элемента. Сначала
  посмотри CI trace/log и фактический DOM.
- Не меняй тестовый порог баланса для того, чтобы скрыть регрессию
  продолжительности партии.
- Не помечай тест `skip`/ `fixme` без объяснения причины, issue и решения
  владельца.

## Перед передачей изменений

Для любой задачи: `npm run build` и `npm test`.
Для UI, текста, магазина, HUD или навигации — дополнительно
`npm run test:e2e`. Для экономики/цен/эффектов — `npm run balance:report`
и полный баланс-тест. В отчёте разделяй:
- какие проверки реально запущены и прошли;
- какие проверки не запускались и почему;
- какие проверки завершились ошибкой и что именно упало.

Не объявляй CI зелёным по одному успешному build или deploy job.

## Длительные симуляционные тесты

- Разделяй CPU-bound тесты симулятора на отдельные файлы так, чтобы один файл
  не выполнялся более 60 секунд. У worker RPC Vitest есть внутренний
  таймаут, который не увеличивается через `testTimeout` (падение наблюдалось
  на Vitest 3; после перехода на Vitest 4 правило сохранено): большой файл
  может завершить все assertions, но уронить раннер на `onTaskUpdate`.
- Не маскируй эту проблему увеличением `testTimeout`: разделяй сценарии на
  независимые группы и сохраняй все проверки.
- В `vitest.config.ts` стоят `pool: 'threads'` и `maxWorkers: 1`: симуляции
  CPU-bound, и один worker исключает конкуренцию двух длинных прогонов на
  CI runner. `tests/harness.test.ts` следит, чтобы эти значения и текст
  навыка не расходились.
