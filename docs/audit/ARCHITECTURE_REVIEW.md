# Архитектура и сопровождение

## Фактическая схема

`src/content/*.json` → `loadContent` и проверка контента (`src/core/content.ts`) → `Game` с `GameState` (`src/core/game.ts`, `state.ts`, `types.ts`). Чистые расчёты `economy/derived/effects.ts → market.ts → financial-rates.ts → derived.ts`, маршрутизация `sales.ts`, покупка `purchases.ts`, расчёт кассы `accounting.ts`. `main.ts` связывает game с UI, storage и эффектами; UI-виджеты получают состояние и команды, `shop.ts` непосредственно вызывает checkBuy; `storage.ts` оборачивает localStorage. Сборка Vite, GitHub Actions CI build/test/e2e и deploy Pages после CI на main. См. `.github/workflows/ci.yml`, `deploy.yml`.

`Game.update` разбивает dt на шаг не более 50 мс, каждый шаг обновляет часы, derived, добычу, отгрузку, финансовые начисления, таймеры/события и достижения. `main.ts` использует rAF, tick 100 мс, ограничивает delta 250 мс, обновляет UI по dirty-флагу не чаще 200 мс. Скрытие сохраняет, возвращение применяет capped offline и обнуляет аккумулятор. Обработчики окна, таймеры и rAF живут весь срок единственного boot; утечка при штатном однократном boot не доказана, повторный mount/unmount не имеет явного disposal-контракта.

## Состояние и надёжность

`normalizeState` проверяет числа/уровни, мигрирует достижения и скважины, ограничивает импорт скважин 5000 (`state.ts:53–175`); `storage.ts:22–52` ловит ошибки, сохраняет повреждённый сейв отдельно. Есть localStorage quota/сбой: `main.ts:323–329` предупреждает. Это не транзакционный многовкладочный storage: межвкладочная гонка и политика конфликтов не проверены. Сейв локальный, серверной авторизации нет. `Game.state` публичен, `window.__game` доступен в браузере, поэтому доверять клиенту для будущих лидербордов нельзя.

Ограничение кеша сумм скважин: WeakMap по массиву и длине (`production.ts:8–16`, F10). Derived сбрасывается вручную при мутациях; сохранение прямого доступа создаёт неявный контракт. Реальные циклы импортов не установлены; нужен CI-инструмент до утверждения об их отсутствии. `types.ts` (~762 строки) сосредоточивает состояние, контент и presentation DTO; разбиение допустимо после стабилизации API, а не самоцель.

## Рекомендуемые границы

1. `core/model`: типы и versioned state, readonly представления, миграции; сохранить JSON-совместимость.
2. `core/engine`: commands buy/flow/update, собственность на мутации, события и RNG; отделить шаг, shipping, покупки, таймеры без изменения порядка исполнения.
3. `core/economy`: чистые расчёты и общие модели потоков; financial settlement остаётся единственной кассой товарной выручки.
4. `infra`: localStorage и clock; UI получает snapshot/селекторы и dispatcher, не экземпляр с мутабельным состоянием.
5. `app`: lifecycle boot/dispose, планировщик и ограниченный catch-up. Worker рассматривать только по профилю и после сериализации команд/событий.

До каждого извлечения: characterization tests состояния, событий и RNG по нескольким seed; сравнивать снимки после последовательности команд и round-trip сейва, при float — заранее согласованная погрешность. Не менять сразу формат сейва, частоту, экономику и UI одновременно. Не заменять движок фреймворком.
