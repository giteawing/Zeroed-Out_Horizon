# Технологический обзор

Исходный стек: TypeScript 5.9, Vite 7, Vitest 3, Playwright, happy-dom; без runtime-зависимостей. `package.json`, `vite.config.ts`, `vitest.config.ts`, `playwright.config.ts`. Vite build выдал 61,88 kB gzip JS — это размер артефакта, не замер скорости на телефоне. Ядро уже не зависит от DOM, поэтому переход ради этого не нужен.

| Вариант | Решаемая проблема / выгоды | Недостатки и сложность перехода | Влияние на производительность | Пригодность / решение |
|---|---|---|---|---|
| Оставить TS + Vite, выделить команды/состояние | F04/F10, ясные границы, минимум зависимостей; сохраняет тесты/экономику | Требуется дисциплина и собственный lifecycle; средняя–высокая поэтапно | Нет принципиальных дополнительных накладных расходов; выигрыш необходимо измерить | Лучший вариант, рекомендован |
| React + локальные selectors/store | Может упростить сложный условный UI и управление lifecycle | Переписывание ручного DOM, новый слой и тесты, риск потерять фокус/поведение, высокая | Зависит от подписок/рендеров; пересчёт ядра не исправляет, есть bundle/runtime overhead | Пока не переходить: текущего доказательства необходимости нет |
| Vue или Svelte | Реактивное представление и компоненты вместо ручного DOM | Компилятор/реактивные контракты, миграция UI и навыков; средняя–высокая | Меньше ручной работы, но эффект на frame time не гарантирован | Пилот одного изолированного экрана только при подтверждённой стоимости UI |
| Zustand/Redux-подобный store | Контролируемые команды, подписки и инспекция состояния | Новая зависимость, serializability RNG/игрового тика, двойной источник истины; средняя | Частые уведомления на 20 экономических подшагов/с могут ухудшить ситуацию | Сначала небольшой типизированный API на TS; store только при реальной потребности |
| Web Worker для симуляции | Перенос измеренной CPU-нагрузки с main thread | Протокол команд, копирование snapshot, ordering, lifecycle, сохранение и детерминизм; высокая | Может снизить блокировку UI, но накладные расходы обмена и общая CPU-нагрузка остаются | Условно, после профилирования и T04 |
| Runtime schema validator (например Zod) | Явная валидация контента/сейва и ошибки | Дублирование типов, размер, совместимость миграций; средняя | Стоимость при загрузке, не каждом тике | Оценить точечно, прежде измерить пробелы текущего normalize/content |
| decimal/bigint | Точность целых сумм выше 2^53 | Дорогая миграция всех формул/сохранений/UI и fractional ставок, высокая | Вероятный CPU/memory overhead, не измерен | Не внедрять до доказанного ущерба и требований к точности (F11) |

Версии уязвимых dev-зависимостей проверить по `npm audit` на дату обновления; предлагаемую audit версию нельзя считать автоматически совместимой. Исследование не включает benchmark альтернатив, UX-эксперименты или проверку цен лицензирования. Архитектурные границы и инварианты важнее выбора модного UI-фреймворка.
