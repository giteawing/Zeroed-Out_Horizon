# Инструкции агентам — «Империя обнуленного горизонта»

Этот файл — короткая точка входа для coding agents. Перед изменениями проверь
рабочее дерево, прочитай подходящий skill из `.agents/skills/` и сверяйся с
реальным кодом. Подробные доменные правила вынесены в skills, чтобы не загружать
весь контекст для каждой задачи.

## 1. Порядок работы

1. Проверь `git status --short --branch`, текущую ветку и последние коммиты.
   Не затирай чужие незакоммиченные изменения.
2. Определи затронутые слои и прочитай соответствующие skills из таблицы ниже.
3. Сначала найди существующий механизм и тесты. Не создавай вторую реализацию
   формулы или игрового правила рядом с уже существующей.
4. Вноси минимальные связанные изменения. Для исправления бага сначала добавь
   регрессионный тест, который воспроизводит его.
5. Запусти проверки, соответствующие изменённым слоям; перед передачей работы
   минимум выполни `npm run build` и `npm test`.
6. Перед итоговым сообщением проверь GitHub Actions именно для текущего HEAD
   `main`: CI должен завершиться с `success`, а workflow **Deploy to GitHub
   Pages** для того же SHA должен завершиться с `success` и содержать
   успешный шаг deploy. Одного build, локальных тестов или промежуточного
   статуса недостаточно.
7. В итоговом сообщении перечисли изменения, выполненные команды и проверки,
   которые не удалось запустить. Не объявляй работу готовой, пока CI и Pages
   не завершились успешно для одного и того же коммита; при ошибке деплоя
   найди её причину и исправь workflow/код, затем повторно проверь публикацию.

Обновляй этот файл и skills только при изменении устойчивых правил проекта,
архитектуры, команд или доменных инвариантов. Не нужно менять документацию
после каждой обычной правки.

## 2. Что за проект

«Империя обнуленного горизонта» — браузерная desktop-кликер-игра про нефтяную
империю. Игрок добывает нефть тапами и скважинами, продаёт её по каналам сбыта,
покупает технику, политику и роскошь, затем достигает финальной цели.

- TypeScript 5.9, Vite 7, Vitest 3, Playwright 1.
- Node.js 22 используется в CI; зависимости фиксируются в `package-lock.json`.
- Приложение статическое, сохранение — в `localStorage`; backend и внешние
  сервисы для игрового цикла не нужны.
- Текущая целевая платформа — desktop Chromium. Не возвращай мобильные проекты
  и мобильную вёрстку без отдельного решения владельца.

## 3. Источники истины

При противоречиях не копируй поведение из старой документации вслепую.

1. Явные актуальные указания владельца.
2. Исполняемый код и действующие тесты — фактическое текущее поведение.
3. `src/content/config.json`, `upgrades.json`, `texts.json` — текущие
   параметры, покупки и пользовательские тексты.
4. `AGENTS.md` и профильные skills — рабочие правила и объяснение инвариантов.
5. `docs/TZ.md` — исходное историческое ТЗ. В нём есть решения, которые позже
   были изменены (например, мобильная поддержка); такие места не являются
   автоматическим указанием вернуть прежнее поведение.

Если обнаружил расхождение кода, теста и документации, сначала установи,
какое поведение актуально и почему. Не «чинить» тест простым ослаблением
проверки, пока не проверена сама логика.

## 4. Архитектура и границы

- `src/content/` — конфигурация игры, определения покупок и весь UI-текст.
- `src/core/` — типы, экономика, состояние, движок, симулятор; не зависит от DOM.
- `src/ui/` — DOM и представление; не дублирует формулы экономики.
- `src/main.ts` — композиция приложения, цикл обновления, сохранения и обработчики.
- `src/styles/`, `src/fx/`, `src/audio/` — оформление, эффекты и звук.
- `tests/` — unit/regression, DOM, balance и Playwright E2E.
- `scripts/` — генераторы графики и инструменты балансировки.

Не переносить расчёты из `core/` в UI. Не добавлять русские пользовательские
строки непосредственно в `src/ui/`: используй `src/content/texts.json` и
`src/ui/texts.ts`. При добавлении типа эффекта проверь всю цепочку:
`types.ts` → `economy.ts` / `game.ts` → `simulator.ts` → описание эффекта
в магазине → тесты.

## 6. Команды разработки и проверки

```bash
npm ci
npm run dev
npm run build          # tsc --noEmit + vite build
npm test               # все Vitest unit/DOM/balance тесты
npm run balance        # только два набора балансировочных тестов
npm run test:e2e       # Playwright против собранного приложения
npx playwright install chromium  # один раз перед локальным E2E
npm run balance:report # отчёт симулятора по профилям
npm run balance:auto   # только отчёт, файлы не записывает
npm run art            # генерирует SVG; перезаписывает графические файлы
```

Перед передачей изменений минимум: `npm run build && npm test`. Для UI и
навигации запускай также `npm run test:e2e`. E2E собирает приложение и
проверяет его через `vite preview` на порту 4173, поэтому это проверка
production-сборки, а не только dev-сервера. В CI последовательность описана
в `.github/workflows/ci.yml`.

**Осторожно с изменяющими файлы скриптами:**

- `npx tsx scripts/auto-balance.ts --write` перезаписывает
  `src/content/upgrades.json` и `src/content/config.json`. Запускай только
  при явной задаче на перекалибровку и внимательно проверяй diff.
- `npm run art` перезаписывает SVG в `public/images/`. Не запускай просто
  «для проверки», если задача не связана с генерацией графики.
- Не меняй lockfile вручную; при изменении зависимостей используй npm и
  проверяй воспроизводимость через `npm ci`.

## 7. Правила Git и публикации

- Для задач, которые владелец поручает агенту напрямую в этом рабочем
  пространстве, по умолчанию работай непосредственно в `main`: после
  проверок коммить изменения и отправляй их в `origin/main` без создания PR.
  Feature-ветку и PR используй, когда владелец прямо просит такой процесс,
  либо когда прямую запись блокируют права/защита ветки.
- Явная команда владельца «слей/мержи в main», «пуш сразу в main» или
  эквивалентная формулировка является достаточным разрешением на прямое
  слияние и push. Не запрашивай повторного подтверждения и не создавай
  дополнительный PR; сначала проверь актуальный HEAD `main`, diff и CI.
- Не делай force-push, reset чужой истории, массовое удаление веток или
  автоматическое слияние PR без отдельного указания владельца.
- Перед публикацией проверь diff, тесты и актуальный HEAD целевой ветки.
  При изменении HEAD во время работы пересобери коммит от новой вершины;
  не перезаписывай конкурентные изменения.
- Не коммить секреты, локальные файлы, `dist/`, отчёты Playwright или
  пользовательские сохранения.

### Слияние feature-веток: fast-forward и rebase

- Если история позволяет, сливай feature-ветку в `main` через **fast-forward**:
  `git merge --ff-only <ветка>`. Не используй `--no-ff`, когда
  fast-forward возможен и отдельный merge-коммит не требуется.
- Перед слиянием проверь чистое рабочее дерево и актуальную вершину `main`.
  Не начинай merge при незакоммиченных изменениях; не включай в него чужую
  работу.
- Если истории `main` и feature-ветки разошлись, сначала перенеси feature
  на актуальную вершину `main`, затем выполни fast-forward:
  ```bash
  git status --short
  git fetch origin
  git switch <feature-ветка>
  git rebase origin/main
  # разрешить конфликты, затем для каждого:
  git add <исправленные-файлы>
  git rebase --continue
  # после успешного rebase:
  git switch main
  git pull --ff-only origin main
  git merge --ff-only <feature-ветка>
  ```
- Если конфликт нельзя корректно разрешить, не угадывай и не выбрасывай
  изменения: останови rebase через `git rebase --abort`, изучи конфликт и
  сообщи о блокере.
- После rebase обязательно запусти проверки, относящиеся к изменённым слоям,
  как минимум `npm run build` и `npm test`. Для UI — также
  `npm run test:e2e`; для экономики и цен — `npm run balance:report`.
- Если feature-ветка уже опубликована, после её собственного rebase обновляй
  удалённую ветку только безопасным lease:
  `git push --force-with-lease origin <feature-ветка>`. Это допустимо
  только для своей feature-ветки и только после проверки, что удалённая
  вершина не содержит чужих коммитов. **Никогда не делай rebase или
  force-push ветки `main`** и не переписывай общую историю.
- После интеграции проверь, что PR закрыт как merged либо что итоговый
  commit находится в истории `main`. Для fast-forward дополнительно проверь
  `git merge-base --is-ancestor <feature-ветка> main`; после squash-merge
  исходная вершина feature-ветки не обязана быть предком `main`.
- Публикуй изменения только после успешных локальных проверок. Для задач от
  владельца используй прямой push в `main` по правилу выше; PR-процесс
  применяй, когда его прямо запросил владелец либо прямую запись блокируют
  права/защита ветки.
- Финальное подтверждение готовности — только после двух успешных workflow
  на одном SHA: CI (build, unit/DOM/balance, desktop E2E) и Deploy to GitHub
  Pages (build + deploy). Проверяй `head_sha`, `status`, `conclusion` и
  финальный deployment job. Не путай queued/in_progress с успешным.
  Если CI или deploy упал/завис/пропущен, работа не считается опубликованной.

## 8. Ключевые запреты

- Не ломай разделение `core/` и `ui/`.
- Не считай нефть деньгами: кошелёк пополняется от продажи, а не от добычи.
- Не включай разлитую нефть/продукты в выручку.
- Не меняй баланс «на глаз» — см. skill `balance-tuning`.
- Не удаляй регрессионные тесты и не ослабляй их только ради зелёного CI.
- Не меняй формат/версию сохранений без проверки миграции старых сейвов.
- Не переименовывай SVG-слои `#cones`, `#btn-body`, `#splashes`,
  `#casing`, `#rig`, `#strata` в `drill.svg`: на них завязана анимация.
